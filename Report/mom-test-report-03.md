## 1. 표면 문제 (잘못된 정의)

- "현장용 **단위 변환 앱**을 만든다."
- "**cmd 없는 GUI 프로그램**을 만든다."
- "**입력 형식 자동 인식** 변환기를 만든다."
- "**현장에서 쓸 수 있는** 스마트폰 변환기" (솔루션 포장)

→ 사용자는 앱을 요청하지 않음. 고통은 **형식·프롬프트·반복 입력·집중 단절**.

---

## 2. 진짜 문제 (한 문장)

현장·사무실에서 치수를 환산할 때 **엄격한 입력 형식·다단계 프롬프트·반복 수동 입력** 때문에 시간이 새고, 실제 업무는 **핸드폰·인터넷 변환**에 의존하며 **업무 집중이 끊긴다**.

---

## 3. Mom Test 증거 3줄

1. > "meter: 2.5 … 형식이 올바르지 않다고 하면서 처음부터 다시 시작해서 시간을 허비" — **5분** (방금)
2. > "인치 치수 … 하루에 10번도 넘게 … 1분이상씩 … 집중력이 흐려" (현장)
3. > "핸드폰에 순차적으로 입력해. 지우고 입력하고 지우고 입력하고" (다중 치수)

---

## 4. 인터뷰 요약

### Q1. 최근 곤란

`meter: 2.5` 입력 후 즉시 결과 기대 → 추가 입력 요구 → 형식 오류 → 처음부터 재시작.

### Q2. 현재 변환 방식

현장 **핸드폰 계산기** — 장갑 벗어야 불편, 숫자+버튼은 편함.

### Q3. UnitConverter.py

방금 테스트 1회 — 형식 맞추기 부담으로 **바로 포기**. (공백 `meter: 2.5` vs `meter:2.5` 가능성)

### Q4. 손실

**5분** (방금 CLI 시도).

### Q5. 인치

매일 사용. 현장은 **핸드폰·인터넷 변환기** — **10회+/일**, **1분+/회**, 집중 단절. cmd는 현장 부적합(컴퓨터 전제).

### Q6. 여러 치수

핸드폰에 **순차 입력·지우기 반복**.

---

## 5. 갭 분석 (관찰, 솔루션 아님)

| 인터뷰 행동/손실 | 현재 CLI | 갭 |
|------------------|----------|-----|
| 즉시 1값 → 결과 기대 | 다중 프롬프트(일괄 안내·빈 줄·재입력) | **단건 UX**와 기대 불일치 |
| `meter: 2.5` (공백) | `meter:2.5` SSOT | **공백 허용** 없음 → 형식 오류 |
| 현장 10회+/일 1분+ | cmd·PC 전제 | **현장 경로 없음** — 핸드폰 유지 |
| 다중 치수 지우기 반복 | 일괄 입력 있으나 cmd | 현장에서 **미사용** |
